# 网络是怎么传输的?
## 1. 集线器
![image.png](https://images.sueryeto.cn/images/20260802105101129.webp)
1. 集线器:无脑将传进来的数据包转发到所有的出口
2. MAC地址:每台电脑具备的地址属性,格式为xx:xx:xx:xx:xx:xx.发送数据包时加入源MAC地址和目标MAC地址,作为接收方的电脑看到信息不是发给自己的就会主动忽略.但是为了避免其他人还是能看到自己无关信息的缺点,人们发明了交换机.
## 2. 交换机
![image.png](https://images.sueryeto.cn/images/20260802105826281.webp)
1. 在交换机的内部维护着一张Mac地址表,记录着每一个设备的MAC地址连接在它的哪一个端口上.
2. 最开始的MAC地址表是空的,交换机通过**学习**的方式逐渐建立起MAC地址表:最初交换机发现目标MAC未知(第一次通信),发起临时广播,把数据包发送给所有电脑(与集线器功能类似),但是偷偷把流经自己的数据包携带的发送方的MAC地址和端口记录下来了,当接收方响应这个数据包时,又把接收方的MAC地址和端口进行记录.等下次发送信息时表里就有映射关系了,就无需再把数据包发送给所有人了.
- 交换机与集线器的比较:

| 项目    | 集线器 HUB     | 交换机 Switch  |
| ----- | ----------- | ----------- |
| OSI层级 | 1层 物理层      | 2层 数据链路层    |
| 转发方式  | 全部端口广播      | 根据MAC精准转发   |
| 带宽    | 所有端口共享带宽    | 每个端口独立带宽    |
| 双工模式  | 半双工         | 默认全双工       |
| 冲突域   | 全部端口同属一个冲突域 | 每个端口独立冲突域   |
| 现在用途  | 几乎淘汰,仅抓包实验  | 家庭/机房标准扩展设备 |
## 3. 路由器
![image.png](https://images.sueryeto.cn/images/20260802133005444.webp)
1. 路由器的功能:作为一台独立的拥有MAC地址的设备,并且可以帮忙把数据包做一次转发.==路由器的每个端口都有独立的MAC地址.==
2. 左边交换机只要多出一条与路由器MAC地址与其端口的映射关系,就可以成功地把数据包转交给路由器,后面的事情暂时不归交换机来管了.
>**问题**:如何把不能直接通过交换机传递给另一台电脑的数据包通通先发给路由器呢?
>**解答**:我们先做假设:能不能直接对每台电脑的MAC地址做手脚?如下图所示:
>![image.png](https://images.sueryeto.cn/images/20260802134149859.webp)
>把所有带RR-RR-...开头的目标MAC地址都先发给路由器.尽管理论上可行,但是现实因素并不允许这样.原因如下:
>**我们先看MAC地址是怎么组成的:**
>**MAC地址也叫做物理地址/硬件地址,长度为48位.其中前24位代表网络硬件制造商的编号,后面24位是厂家自己分配的(一般表示系列号),MAC地址类似于身份证号,在全世界范围内都是唯一的.所以在你组网之前,MAC地址就已经是固定的了,不能更改.**
>因此,我们需要给电脑起一个新的,并且随时都能改动的名字.我们姑且先用32位的0101编号,但可能有些不清晰,于是把它们分为4个部分,中间用点相连(比如11000000.10101000.00000000.00000001),但可能还是不够清晰,所以我们可以把它们转成十进制(比如转成192.168.0.1),就这样,==IP地址==就产生了.
3. IP地址的应用:我们先把各个设备的IP地址分配好(路由器两个端口分别分配两个IP地址)
![image.png](https://images.sueryeto.cn/images/20260802135336562.webp)
比如我想把数据包发送给C或者D,那么可以用这么一句话来描述:
==将IP地址为192.168.1开头的全部先发送给路由器,之后的事情交给它.==
现在两个设备之间的传输除了之前数据链路层头部的信息之外,还需要加一个网络层的头部,如下图所示:
![image.png](https://images.sueryeto.cn/images/20260802135841794.webp)
假如A给B发送数据,由于它们直接连着交换机,所以A发出这样的数据包就可以直接通过数据链路层经过交换机发送出去,其实网络层在其中就没有起到作用.
如果A给C发送数据,就需要通过A -> 路由器 -> C这样的路径进行传输,A需要先转交给路由器,再由路由器转交给C.
所以先把目标IP先改成C的,由于最底层的传输仍需依赖数据链路层,因此包要分成两段来发送:A要先把数据包发给路由器,所以目标MAC地址要改成路由器的.如下图所示:
![image.png](https://images.sueryeto.cn/images/20260802140511616.webp)
数据包传输给路由器之后,这时候路由器就有个神奇的功能:它可以根据目标IP地址把目标MAC地址给改成目标IP地址对应的MAC地址(即C的MAC地址),如下图所示:
![image.png](https://images.sueryeto.cn/images/20260802141123343.webp)
随后再通过路由器 -> C的路径顺利把数据包传给C.任务完成!但是有下面几个问题亟需解答:

>**问题一**:A给C发送数据包,怎么知道是否需要通过路由器转发呢?
>**解答**:==通过子网.==
>![image.png](https://images.sueryeto.cn/images/20260802141609665.webp)
>**什么叫属于同一个子网?**
>我们先看一张图:
>![image.png](https://images.sueryeto.cn/images/20260802142147130.webp)
>用人话:对A来说,只要是192.168.0开头的,和它在同一个子网,否则就是不同子网.
>但是对于计算机来说,怎么分辨是否处于同一子网?我们引入一个概念:==子网掩码==.它可以解决这个问题.
>假如A的子网掩码是255.255.255.0,将源IP(A的IP地址)与目的IP分别同这个子网掩码进行与运算(&),相等则在同一个子网,不相等在不同子网.
>==IP地址 和 子网掩码 逐位二进制按位与（Bitwise AND），算出网络地址，用来判断两台主机是否在同一个子网。==
>	举个例子:如果A的IP地址是192.168.0.23,子网掩码是255.255.255.0.算下来网络地址就是192.168.0.0,则剩下的B,C,D算下来应该是如下:
>	![image.png](https://images.sueryeto.cn/images/20260802143655502.webp)
>	记忆规律:1. 子网掩码中为`255`的段:与运算之后**保留IP原来数字**;
>	2. 子网掩码为`0`的段:与运算之后**直接变成0**.
>按照这个逻辑回到刚刚的网络结构中,左边就是处于同一个子网,右边也处于同一个子网,但是两边属于不同的子网:
>![image.png](https://images.sueryeto.cn/images/20260802144105768.webp)
>所以当A想把数据包发给C时,就会先进行如下运算:
>![image.png](https://images.sueryeto.cn/images/20260802144243274.webp)
>随即发现不相等,即A和C不是同一个网络地址,并不处于同一个子网.所以A会直接把数据包发给路由器,后面发生的事情就不归A关心了.

这下第一个问题解决了,自然产生下一个问题:

>**问题二**:A如何知道哪台设备是路由器呢?
>**解答**:==在A上要设置默认网关==.默认网关就是个IP地址,相当于告诉电脑A:当遇到不是处于同一子网的电脑时,先把包发给这个IP地址,在这里自然指的是先发给路由器.
>![image.png](https://images.sueryeto.cn/images/20260802144930267.webp)

这下问题二解决了,但又伴随着下一个问题:

>**问题三**:我怎么知道路由器的MAC地址?
>**解答**:==ARP协议==.
>我们先把问题简化成A发数据包给B时,我们直接把B的MAC地址写在了数据链路层.如下:
>![image.png](https://images.sueryeto.cn/images/20260802145758821.webp)
>但实际上一开始的时候我们并不知道B的MAC地址是什么,只知道B的IP地址是多少.这个时候是谁把B的MAC地址填在了数据链路层头部的?其实这里就利用了ARP协议的机制,它可以将某个IP地址映射到MAC地址上.和之前的MAC地址表类似,A也存着一张ARP缓存表,记录着IP与MAC地址的对应关系,如下图所示:
>![image.png](https://images.sueryeto.cn/images/20260802150440374.webp)
>同样,一开始的ARP表是空的,需要进行一轮ARP请求来把表中数据填上.在进行ARP请求过程中,就会引申出一个网络安全概念:ARP欺骗.我们先按下不表.
>填上ARP数据后,如果A还想给B发送数据包,就可以通过ARP表直接把B的MAC地址写在数据链路层头部了.
>现在,我们已经可以成功把任何一个数据包发送出去了.在同一个子网,就通过交换机在数据链路层的以太网内发送到目的地;不在同一个子网,就把包丢给路由器.

由此,下一个问题就呼之欲出了:

>**问题四**:路由器怎么把包再往下传递呢?
>**解答**:==路由表==.
>路由器中的路由表大概是这样的:

| 目的地址范围      | 端口  |
| ----------- | --- |
| 192.168.0.x | 0   |
| 192.168.1.x | 1   |
>当处于路由器 -> C这个状态下时:
>![image.png](https://images.sueryeto.cn/images/20260802152359706.webp)
>路由器发现目标IP的范围处于192.168.1.x,因此决定从端口1发送数据包,当然这个时候路由器也要做一下ARP获取到C的MAC地址,然后把包丢过去就行了,剩下的就是以太网内的事了.
>路由表中可能还含有一个"下一跳"地址,表示如果这个包不能直接传到目的地,可以再转交给下一个路由器来处理.如下图所示:
>![image.png](https://images.sueryeto.cn/images/20260802152928154.webp)
>A和C之间可能要经过很多路由器中间协作才能把包传过去.

## 4. 补充: DNS 与 NAT

### DNS(域名系统)
IP地址(如192.168.0.1)不方便人类记忆,所以我们用域名(如www.baidu.com)来代替.DNS的作用就是把域名翻译成IP地址:
- 浏览器输入域名 → 向DNS服务器发起查询 → DNS返回对应的IP → 浏览器用IP发起真正的请求.
- 查询顺序:先查浏览器缓存 → 本地hosts文件 → 递归查询DNS服务器.

### NAT(网络地址转换)
- 问题:IPv4地址总共只有约43亿个,全球设备远超这个数,公网IP不够用.
- 解决:家庭/公司内部使用**私有IP**(如192.168.x.x、10.x.x.x),通过路由器上的NAT将内网IP+端口映射为路由器的公网IP+端口,实现多台设备共用一个公网IP上网.
- 副作用:外网无法主动访问内网设备,因此催生了"内网穿透"等技术.

# 网络是怎么可靠的?
## 1. 进程到进程之间通信的实现
回顾上节,网络的传输其实很简单,就是按照如下的过程进行:
![image.png](https://images.sueryeto.cn/images/20260802161322993.webp)
问题很快也会显露出来:
前三层协议只能把数据包从一个电脑搬到另外一台电脑,但电脑中其实是有很多程序的,具体发给哪个程序或者说进程,其实并没有说明.所以我们现在需要把电脑里的进程区分开来.于是我们就给每个进程分配了数字编号,命名为=="端口号"==.就像如下的图片:
![image.png](https://images.sueryeto.cn/images/20260803092239818.webp)
现在开始,发送数据包就不是电脑A -> 电脑B那么简单了,而是电脑A的一个端口发送给电脑B的一个端口(比如电脑A浏览器的12345端口发送给电脑Bweb的80端口),此时当我们传输数据包时,不仅仅是要加上数据链路层和网络层的头部,还需加上一个传输层头部.比如下面这样:
![image.png](https://images.sueryeto.cn/images/20260803092616067.webp)
由此,我们实现了从主机到主机的通信升级到了进程到进程的通信.这就是==UDP协议==的部分实现.

- TCP与UDP的对比:

| 特性 | TCP | UDP |
|------|-----|-----|
| 连接方式 | 面向连接(需三次握手) | 无连接 |
| 可靠性 | 可靠交付(确认+重传) | 尽力而为,不保证送达 |
| 顺序保证 | 有序(序号+累计确认) | 不保证顺序 |
| 流量控制/拥塞控制 | 有(滑动窗口+拥塞窗口) | 无 |
| 头部开销 | 20字节 | 8字节 |
| 典型应用 | HTTP、FTP、SSH、电子邮件 | DNS、视频直播、VoIP、在线游戏 |

## 2. 网络可靠性的提高方案
- 在UDP协议下,电脑间自然可以无忧无虑的互相聊天了.但是有些问题仍然亟需解决:由于网络环境的不可靠,数据包很有可能在半路丢失,提高数据包传输的可靠性就显得尤为重要.
引入:假设有A和B两台电脑之间互相进行通信,怎么提高它们之间通信的可靠性?

>这个问题的答案并没有那么复杂,我们先回答如下两个问题,答案十分简单粗暴:
>
>**问题一**:A怎么知道包丢了?
>**解答**:让B告诉A.
>**问题二**:丢了的包怎么办?
>**解答**:重传.

==所以我们可以这么设计:==
### a. 停止等待协议(可靠交付)
![image.png](https://images.sueryeto.cn/images/20260803094014447.webp)
如上图所示,A每发一个包都需要得到B的确认ACK之后再发下一个包.否则如果在一定时间内没有得到确认,A就向B重传这个包.这就是**停止等待协议**(Stop-and-Wait)的原理.
虽然A无法保证B一定能收到包,但是A能够确认B是否收到了包.收不到就重试,尽可能让这个通信变得可靠.所以这个过程又有了个新的特征:==可靠交付==.
停止等待虽然能解决问题,但是效率太低了.
- 改进:流水线机制(Pipeline)
我们于是开始尝试像流水线一样把数据包传给B,不再等待确认包传回再传新的包.但是这就引发了一个新的问题:有的时候A发出的数据包分别走了不同的路由到达了B,这就可能无法保证它们和发送数据包时是同一个顺序,所以我们开始改进这个方案:
在发送的数据包里加上序号同时B在相应的确认包上也加上一个确认号.
>注意:ACK包上的确认号实际上是收到的最后一个数据包的序号加一(seq+1),也就是告诉对方下一个应该发的序号是多少.

==累计确认/累计应答==机制:接收方返回的ACK确认号 = 期望收到的下一个报文段序号.
含义:"这个序号之前的所有分组,全部已经正确收到."
举例:ACK确认号为5,代表着0,1,2,3,4号分组全部完整收到,现在等待接收5号分组.

经过改进后的流水线机制,我们提高了通信效率.但是伴随着一个新的问题:有的时候A发送数据包的速度过快,而B的接收能力不够,但B却没有告知A这个情况,怎么解决呢?
>很简单,B告诉A它的接收能力,A相应地控制它发送数据包的速度就可以了.但B要怎么告知A它的接收能力呢?

B决定每次发送数据包给A时顺便传来一个值叫做**窗口大小**.这就是表示B的接收能力.
![image.png](https://images.sueryeto.cn/images/20260803100919288.webp)
同时A给B发送数据包的时候也会带上自己的窗口大小表示A的接收能力.
那么现在它们都知道对方的窗口大小,A应该怎么利用它来控制数据包的流量呢?
### b. 滑动窗口机制
假如B给A传来的窗口大小为5,那么A可以把自己要发送的数据分成如下四类:
![image.png](https://images.sueryeto.cn/images/20260803101635480.webp)
当A不断发送数据包时,**已发送的最后一个序号**向右不断移动,直到碰到了**窗口的上边界**,此时A就无法继续发包,达到了流量控制.但是A不断发包的同时,也会收到来自B的确认包(ACK),整个窗口就会往后移动,因此**上边界**也往右移动,所以A就能发更多数据包了.
- 以上都是在窗口大小不变的前提下,而B发给A的ACK包中每一个都会重置一个新的窗口大小.
1. 当A收到的确认包里有(ACK = 4  WIN = 6),那么**窗口上边界**再向右移动一格,实现窗口大小的扩大.
![image.png](https://images.sueryeto.cn/images/20260803102940142.webp)
2. 当A收到的确认包里有(ACK = 5  WIN = 4),那么**窗口的下边界(收到的最后一个确认号)** 向右移动一格,实现窗口大小的缩小.
![image.png](https://images.sueryeto.cn/images/20260803103146498.webp)
>注:WIN从6缩小到4,通常意味着B的接收缓冲区空间变紧张了(比如上层应用处理数据变慢),A需要相应减慢发送速度.
### c. 网络拥塞问题的解决
网络拥塞控制与流量控制类似,但流量控制受B的接收能力的影响,拥塞是受网络环境的影响.拥塞控制的解决办法依旧是设置一个窗口值.与B直接告诉A窗口大小的流量控制不同,网络环境的情况是不能直接得知的.所以只能让A单方面地对网络环境的试探,不断感知网络环境的好坏,从而确定自己的拥塞窗口的大小.
- 最终,通信窗口取决于拥塞窗口和滑动窗口的最小值(木桶效应).

### d. TCP协议(三次握手)
- 如果A发送数据包时B还没有接收能力(关机了或者是其他情况),这就会导致一定程度的浪费.这个问题在于A和B通信之前没有预先确认B是否已经准备好了就开始传输数据包.
原理:
1. A -> B : SYN, seq=x (A向B发出连接请求,携带初始序号x);
2. B -> A : SYN + ACK, seq=y, ack=x+1 (B同意连接,告知A下一个期望收到的序号是x+1);
3. A -> B : ACK, seq=x+1, ack=y+1 (A确认收到B的同意,连接正式建立).

三次握手完成后,双方各自确认对方的收发能力正常,随后即可开始传输数据.
### e. TCP协议(四次挥手)
- 连接可以建立,自然也有关闭的时候.TCP断开连接需要四次交互,称为"四次挥手":
1. A -> B : FIN, seq=u (A没有数据要发了,请求关闭连接);
2. B -> A : ACK, seq=v, ack=u+1 (B确认收到,但B可能还有数据没发完);
3. B -> A : FIN, seq=w, ack=u+1 (B的数据也发完了,请求关闭);
4. A -> B : ACK, seq=u+1, ack=w+1 (A确认关闭).

A发送完最后一个ACK后进入 TIME-WAIT 状态,等待 2MSL(最长报文段寿命,约2分钟)后关闭;B收到ACK后立即关闭.
>为什么需要四次而不是三次?因为TCP是全双工的,每个方向都需要独立关闭.A说"我没数据了"(FIN),B说"知道了"(ACK),但B可能还有数据要发;等B也发完了,再发FIN,最后A确认.所以比三次握手多了一次交互.

## 3. HTTP 协议基础

# 网络是怎么安全的?
- 引入: 两台电脑之间的通信必须通过中间人来传递,怎么避免中间人窃听或篡改信息呢?
## 1. 对称加密
- 首先我们先引进==密钥==的概念:密钥就是加密算法使用的"秘密参数",没有正确密钥,就算知道加密算法也无法对密文进行解密.
==对称加密==的定义:加密和解密使用同一个密钥.
工作流程:
1. 通信双方提前协商好一把共同密钥（Secret Key）
2. 发送方：明文 + 密钥 → 加密算法 → 密文，通过网络发送
3. 接收方：密文 + 同一把密钥 → 解密算法 → 还原出明文
但是密钥也是要通过中间人进行传递的,对称加密的方式并不能保证这个密钥能安全地传给对方,存在着密钥泄露的风险,因此我们需要更好的加密手段.
## 2. 非对称加密
==非对称加密==中,加密和解密使用两套不同,数学配队的密钥,分为**公钥**和**私钥**,一对密钥同时生成,天生配对.

>一条原则:**公钥加密,私钥解密**.

**基础规则**:
1. 公钥(Public Key): 可以公开分发,谁都能拿到;
2. 私钥(Private Key): 自己永久保存,绝不外泄;
3. 数学特性:用公钥加密的数据,只能用对应的私钥解密.
如果我们把非对称加密的手段用来传递对称加密的密钥是不是就能实现更高效的加密传输?我们可以讨论这一个方案:
假设有A,B两方想要互相通信,A准备一套公钥和私钥,B准备一个对称加密密钥M,现在的目的就是把M安全地从B手中传递到A手中.
A将公钥通过中间人传递到B手中,然后B用公钥加密密钥M再传递给A,让A用私钥解密,这下双方有相同的密钥M,就可以互相地进行安全通信了.
但真有这么简单吗?公钥的传输依然是明文,虽然不担心中间人看到他,但是你就不怕中间人会从中篡改公钥吗?
==**中间人攻击**==:
当A把公钥传递给B时,中间人直接把公钥扣下,替换成自己伪造的公钥传给B.随后B就会用伪造的公钥加密密钥M,此时中间人是可以用他手中**伪造的公钥对应的私钥**解密出M,成功获取了A和B之间对称加密的密钥M.同时中间人再用真正的公钥B加密M,然后发给A.对A来说,用私钥解密出M是顺理成章的事情,没发现任何问题.对B来说,他拿到了公钥(他并不知道公钥被中间人伪造过)并加密了M传递给A,也没发现任何问题.
![image.png](https://images.sueryeto.cn/images/20260803142657927.webp)
但中间人已经掌握了对称加密公钥M,A和B此后的通信都会被中间人窃听.因此这个加密手段依然不够安全.
我们可以先看下图:
![image.png](https://images.sueryeto.cn/images/20260803142907373.webp)
A先对要发送的数据计算一个哈希值(摘要),然后用另一套私钥对这个哈希值加密,生成**数字签名**,连同原始数据一起发给B.B收到后,用对应的公钥解密签名得到哈希值,再自己对原始数据计算哈希值,两个哈希值一致则说明数据没有被篡改、且确实来自A.因此,**签名**就实现了它的功能.
![image.png](https://images.sueryeto.cn/images/20260803144440181.webp)
但此时,另一套用来验签的公钥也是属于明文传输,怎么防止它不被篡改呢?
- 我们需要引入一个可信的第三方:**CA(证书颁发机构)**
CA的工作方式:A先把公钥b以及自己的身份信息提交给CA,CA将公钥b、持有者信息、有效期等打包成一个**数字证书**,用CA自己的私钥X对证书的哈希值签名,生成证书发给A.A拿到证书后,在与B通信时将证书发给B.B用内置的CA公钥Y验证证书的签名:如果签名有效,说明证书内容没有被篡改,B就能信任其中的公钥b确实是A的.如果签名无效或被未知CA签发,B应拒绝这个通信.
综上,这套安全通信机制就是 **TLS/SSL 协议**的核心思想.TLS作为安全层,配合HTTP协议一起使用,就构成了 **HTTPS(HTTP over TLS)**.
